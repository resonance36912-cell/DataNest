# 17. Security, Privacy, Data Integrity, and Abuse Resistance

## 17.1 Security and privacy

Audit purpose. Assess practical security posture without requesting secrets or destructive testing.

Do not break. Do not exfiltrate, print, or request secrets. No penetration testing beyond non-destructive authorization checks without explicit approval.

[ ] Review RLS coverage, SECURITY DEFINER functions, execute grants, service-role gateways, and direct table write privileges.

[ ] Check Auth settings and outstanding security configuration warnings, including leaked-password protection if still disabled.

[ ] Review CORS/origin policy and JWT enforcement on Edge Functions.

[ ] Check rate limits, replay/idempotency, brute-force/abuse paths, invitation spam controls, and user enumeration leakage.

[ ] Review secret handling in source, runtime config, logs, screenshots, audit events, AI prompts, and exported artifacts.

[ ] Check project isolation and cross-project access for data, memory, Think Tanks, contributions, governance, and artifacts.

[ ] Review audit log completeness and tamper resistance for high-value actions.

[ ] Test unauthorized role transitions and direct RPC/table access from lower-privilege users.

[ ] Assess privacy/retention controls for user-submitted data and AI-derived reusable knowledge.

[ ] Flag any security recommendation that requires destructive or intrusive testing as PROPOSED ONLY unless explicitly authorized.

Evidence to return: Security finding register, privilege matrix, RLS/RPC observations, abuse cases, remediation plan.
