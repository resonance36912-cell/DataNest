# 1. How to Use This Audit Brief

This is both an audit specification and a return template. The external auditor should inspect the live system, source architecture, workflows, and observable outputs; record evidence; identify defects, friction, duplication, risk, and missing controls; and propose optimizations that preserve the system’s governance and security boundaries.

| Evidence rule Do not infer a pass from design intent. Mark each item PASS, PARTIAL, FAIL, NOT TESTED, or NOT APPLICABLE. Every PARTIAL/FAIL finding must include concrete evidence: URL, screen, trace, code path, log excerpt, reproduction steps, or observed output. |

| --- |

1. Review the system baseline and invariants in Sections 2-3 before testing.

2. Audit every domain in Sections 5-20. If access is unavailable, record NOT TESTED and explain what is required.

3. Execute the end-to-end journeys in Section 21 using non-destructive test data wherever possible.

4. Assess output quality, not only whether a button or API call technically completes.

5. Record every material finding using the finding schema in Section 23.

6. Produce the executive summary, prioritized optimization backlog, target-state proposal, and regression plan in Sections 22-26.

7. Return the completed report in a form that can be pasted back into ChatGPT without losing IDs, severity, evidence, or dependencies.

| Optimization posture Prefer simplification, fewer duplicated states, clearer ownership, lower operational cost, higher observability, stronger traceability, and faster user completion. Do not “optimize” by removing independent review, audit history, authorization checks, append-only records, or certification gates. |

# 2. Current System Baseline

The external auditor should validate the baseline rather than assume it is correct. Differences between this baseline and observed reality are findings.

| Area | Current baseline | Audit implication |

| --- | --- | --- |

| Authority chain | GitHub is source authority; Supabase is application/control-plane data authority. | Check for authority drift, duplicate sources of truth, stale local copies, and direct production changes not represented in source/migrations. |

| Hosting | Primary free public host is GitHub Pages; architecture is provider-agnostic; Vercel is optional. | Verify runtime configuration, health markers, portability, and absence of hard Vercel coupling. |

| UNIFI | Planning, project context, Job Manifests, checkpoints, artifacts, audit, human controls. | Audit manifest completeness, traceability, checkpoint continuity, handoff quality, and operator clarity. |

| TranScheduler | Capability-aware queueing, dependencies, reservations, retry/backoff, fairness, timing. | Verify UNKNOWN capability is never treated as execution permission; test retries, dependencies, controls, and recovery. |

| DataNest AI | Governed AI workflow with job/trace linkage, external AI intake, certification, reviewed memory. | Audit AI request attribution, context correctness, result import, memory governance, trend learning, and failure boundaries. |

| Think Tanks | Project channels for discussion, decisions, actions, and reviewed learning. | Verify independent confirmation, action extraction, memory approval, and no automatic authority/points. |

| Contribution Intelligence | Evidence, scoring, reputation, anomaly signals, progression, N0nymous Squad. | Audit fairness, anti-gaming, explainability, eligibility, opt-ins, reviewer separation, and no capital/Sparks weighting. |
